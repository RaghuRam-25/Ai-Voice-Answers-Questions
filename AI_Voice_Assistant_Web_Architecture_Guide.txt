1. What You Are Building
The goal is a voice-first AI assistant for a laptop. The user should not need to click the mouse for normal
interaction. A wake trigger—such as a wake word, keyboard shortcut, or two-clap sound
detector—activates the assistant. The assistant opens its web interface, gives a welcome message, then
asks: “How can I help you?” The user speaks, the system converts speech to text, sends the request to
the AI/command engine, returns an answer, and optionally performs an allowed computer action.
 • Idle → listen for a local wake trigger.
 • Wake detected → show/activate assistant UI.
 • Welcome → play a short spoken greeting.
 • Prompt → “How can I help you?”
 • User voice → speech-to-text.
 • AI/intent engine → understand question or command.
 • Response → text + text-to-speech.
 • Action layer → optionally execute an approved task.
 • Result → tell the user what happened and return to listening.

6. What Each Major Backend Part Does
routes/ — Only defines URL endpoints and connects them to controllers. Keep business logic out of
routes.
controllers/ — Receives HTTP requests, validates/reads data, calls services, and sends responses.
services/ — Contains actual application logic: AI requests, conversation handling, command
interpretation, and database workflows.
ai/ — Keeps prompts, tool definitions, and AI-provider integration isolated so the AI provider can be
changed later.
models/ — MongoDB/Mongoose schemas and database models.
middleware/ — Authentication, validation, rate limiting, error handling, and security checks.
socket/ — Realtime communication between the web UI and backend.
validators/ — Zod schemas for safe, predictable request data.

8. Important Reality: Web App vs Desktop Control
A normal browser web app cannot freely control the whole laptop, launch arbitrary desktop programs,
run shell commands, or access protected OS features. Browser security intentionally prevents this.
Therefore, the web frontend should be the interface, while real laptop control should later be handled by
a small trusted desktop/host application.

Recommended architecture: Next.js Web UI ⇄ Express backend ⇄ Desktop Host/Agent ⇄ Windows OS
The desktop host can be built later as a separate application. It should authenticate to the backend and
expose only explicitly allowed operations. This preserves your requested frontend/backend separation.
9. Wake Trigger Strategy
 • Phase 1 — easiest: global keyboard shortcut or a visible web button. Use this while building the AI core.
 • Phase 2 — wake word: use an OS/desktop-level listener or a supported wake-word engine. Keep
 continuous listening outside the browser when necessary.
• Phase 3 — two-clap trigger: a desktop microphone listener detects two short peaks within a defined
 time window, then activates the assistant. Add noise filtering and a cooldown to reduce false triggers.
• Important: the clap detector should not directly execute dangerous commands. It should only wake the
 assistant.

13. Recommended Build Order
Step 1: Create root project with separate frontend and backend folders.
Step 2: Create Next.js + TypeScript frontend.
Step 3: Create Node + Express + TypeScript backend.
Step 4: Connect MongoDB and create User/Conversation/Settings models.
Step 5: Build the assistant screen: orb/status, transcript, response, microphone state.
Step 6: Add text-only assistant first. Verify API → AI → response before adding voice.
Step 7: Add speech-to-text and text-to-speech.
Step 8: Add Socket.IO for realtime assistant status and streaming events.
Step 9: Add authentication and conversation history.
Step 10: Create a safe command/tool registry. Do not allow arbitrary shell execution.
Step 11: Build the separate desktop host/agent for real OS-level actions.
Step 12: Add wake word/clap detection at desktop level.
Step 13: Add permissions, confirmation for risky actions, logs, rate limits.
Step 14: Test locally, then deploy frontend and backend separately.
14. Safety Model for Computer Control
Do not design the AI as “AI can run any command.” Instead, define a small tool registry. Example: open
application, open URL, search web, create note, read a selected file, control media. Each tool should have
a schema, permission level, validation, timeout, and audit log.
 User: "Open VS Code"
       ↓
AI identifies tool: openApplication
       ↓
Validate { app: "vscode" }
       ↓
Permission check
       ↓
Desktop host executes approved operation
       ↓
Return success/failure
       ↓
AI speaks result
For destructive or sensitive actions—delete files, send messages, make purchases, change security
settings—require explicit confirmation.

16. Development Rules
 • Keep all frontend code inside frontend/ and all backend code inside backend/.
 • Never put MongoDB credentials or AI private keys in frontend code.

• Keep AI provider code behind ai/providers/ so the provider can be replaced later.
 • Keep OS-level control out of the browser; use a separate desktop host.
 • Start with text commands before implementing wake-word/clap automation.
 • Use TypeScript on both frontend and backend for one consistent language.
 • Use environment variables for secrets and deployment-specific URLs.
 • Log important command executions without storing unnecessary sensitive voice data.

18. Bottom Line
Yes—your chosen stack is suitable. You do not need Python for the main web application. Build the web
system with Next.js + TypeScript on the frontend and Node.js + Express + TypeScript + MongoDB on the
backend. The only important addition is a separate desktop host/agent later if you want genuine
laptop-level control, wake-word/clap listening while the browser is closed, or launching desktop
applications.
Recommended first milestone: Get “text → AI → answer” working in the separated frontend/backend
structure. Then add voice. Then add safe computer-control tools. Finally add always-on wake detection.
